# ZenCrypto V53.3 — Partner Execution Foundation

## Current repository assessment

The existing repository is a Vite/React frontend with FastAPI services and a substantial paper-trading implementation. The exchange service currently uses a Binance-oriented CCXT connector and paper matching/ledger modules. The platform README explicitly states that the application is not production-ready and does not execute customer live orders, custody real funds, or process real deposits/withdrawals.

The requested execution partner is not yet selected, no partner API documentation is available, and the provider's legal role is unknown. Therefore this change adds a provider-neutral, fail-closed integration boundary; it does not claim to connect a live venue.

## Decisions

- Execution model: external partner execution.
- Market data: two independently sourced feeds with normalization, freshness and divergence checks.
- Regulatory status: pending.
- Custody objective: eventual own custody; no live custody activation in this change.
- Live customer routing: remains disabled.

## Added foundation

- `exchange-service/partner_execution.py`
  - Normalized order request and execution models.
  - Provider protocol for submit, cancel and order lookup.
  - Unconfigured adapter that always fails closed.
  - Explicit production release gates.
  - Normalized provider order statuses.
  - Timestamped HMAC-SHA256 webhook verification helper.
  - SQLite durable inbox with idempotency and conflicting-payload detection.
- `exchange-service/tests/test_partner_execution.py`
  - Validation, fail-closed behavior, release-gate, status mapping, signature freshness and inbox idempotency tests.

## Integration contract

A future provider adapter must implement the `ExecutionPartner` protocol and be reviewed against the provider's actual API documentation. Provider-specific signing, request canonicalization, symbol mapping, precision, order types, rate limits, cancel/replace semantics, execution reports and account/settlement semantics must be implemented and tested individually.

The webhook verifier documents a generic timestamp-plus-body HMAC format. Do not enable it for a provider until the provider's exact signature scheme and replay protections are confirmed.

## Required next integrations

1. Select the execution provider and verify its regulated role, contractual scope, permitted customer types, products and jurisdictions.
2. Obtain official API documentation and sandbox credentials.
3. Implement provider-specific adapter and contract tests.
4. Add authenticated API routes using the platform's verified user identity and trading eligibility service.
5. Persist ZenCrypto order IDs, provider order IDs and execution IDs with unique constraints.
6. Reconcile partner order state, execution reports, fees, cash movements and settlement statements.
7. Integrate the existing double-entry ledger only after settlement evidence and customer-funds ownership/obligations are defined.
8. Connect Owner Master Console to read-only, permission-scoped operational and financial aggregates.
9. Complete legal, compliance, security, operational resilience and independent financial-control reviews.

## Release gates

Live customer routing must remain disabled unless all of the following are independently approved in the production secret manager:

- `LIVE_TRADING_ENABLED=true`
- `LIVE_CUSTOMER_ORDER_ROUTING_ENABLED=true`
- `PARTNER_PRODUCTION_APPROVED=true`
- `REGULATORY_LIVE_TRADING_APPROVED=true`
- `SECURITY_GO_LIVE_APPROVED=true`

These flags are necessary controls, not proof of legal authorization. A production deployment must also enforce account eligibility, order limits, customer disclosures, partner contract limits, reconciliation controls, monitoring, incident response and tested rollback.

No provider credentials, private keys, customer funds or live order routes are added by this change.
